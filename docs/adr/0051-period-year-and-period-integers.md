# Period identity: `year` + `period` integers replace the `FYxx-Mxx` hierarchy

Period drops its adjacency-list hierarchy (`period.code`/`parent_code`/`order`, `FY26`/`FY26-Q3`/`FY26-M06` string PKs) in favor of two small independent tables: `year` (`year: int` PK, one row per seeded fiscal year) and `period` (`period: int` PK 1–12, `label`, `quarter`, static reference data — quarter is stored per period row, not walked via a parent chain). `Financial`/`DriverFact`/`AppSettings.current_actual_period_code` drop their single `period_code` string FK in favor of `year`/`period` int FKs directly, matching the column names `fact_import.py`'s CSVs already use. `period` is fiscal-relative (period 1 = the fiscal year's first month, not necessarily January) — groundwork for eventual non-calendar-aligned fiscal years, though no company-specific fiscal-year-start configuration is added by this decision; all current data still assumes calendar alignment. No string identifier is stored or synthesized anywhere: URLs/query params use two explicit params (`?year=&period=`), and internal code (tree-building, `DriverEngine`, trend-flagging cache keys) passes plain `(year, period)` pairs. The Year→Quarter→Month tree the Context Bar's picker renders is still computed server-side (a `Year` × `Period` join grouped by `quarter`) — nothing about the picker's shape changes for the frontend. Display keeps the existing `FY26`/`Q3 FY26`/`Jan FY24` convention, now formatted from the int rather than read off a stored label.

Rejected: keeping the adjacency-list hierarchy and only reformatting the `code`'s content (e.g. `2026-06`) — the whole reason a walkable tree existed was to derive Quarter/Year groupings from Month rows; once quarter is arithmetic and year is a plain int, the tree, its `parent_code` walk, and its non-postable rows (Year/Quarter — 5 of every 17 seeded rows) serve no purpose. This supersedes ADR-0025's rejection of separate year/quarter/month columns: that call made sense before real year/period integers existed anywhere in the schema; now that fact imports already carry `year`/`period` as ints, converting the master table to match removes a translation layer rather than adding one. ADR-0025's Month-only-postable rule itself is unchanged.

**Status**: accepted, supersedes ADR-0025's schema choice (see `docs/adr/0025-period-hierarchical-master-data.md`)

**Consequences**: ~40+ call sites across `seed.py`, `seed_vdt.py`, `admin.py`, `fact_import.py`, `calendar/periods.py`, `accounting/tree.py`, `vdt/tree.py`, `drivers/engine.py`, `api/routes.py`, and the frontend period state/store/components construct or parse the old `FYxx-Mxx` string format and need rewriting. Prior-year lookups become `(year-1, period)` tuple lookups instead of a sibling-node walk; the Trailing window's (`docs/adr/0042-vdt-trends-trailing-window.md`) cross-year wraparound becomes explicit int arithmetic instead of a parent-chain walk. Adding a new fiscal year is still a `seed.py` code change + reseed, not a runtime admin action.
